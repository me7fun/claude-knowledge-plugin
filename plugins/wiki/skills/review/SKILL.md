# Wiki Review — 知识盘点

> 所有回复使用用户的对话语言。本 skill 只**提案**，实际写入遵循写入政策（预设：须用户同意）。

核心问题：

> 三个月后有人踩到同一个问题，知识库里该有什么能帮他省下这次调查？

## 步骤 1：回顾对话

回顾对话，找出：碰了哪些系统、解了什么问题、做了什么决策、发现了什么隐藏假设、哪些理解需要跨档拼凑。

## 步骤 2：过滤（完整判准见 reference.md「写什么／不写什么」）

值得提案：跨档架构关系、设计决策与理由、API/后端整合细节、会再踩的坑根因、未成文的惯例。

不值得：读单一档就能知道的、临时 debug 细节、同任务里已记过的、低把握度的猜测。

原则：**少而准**——一条有凭有据的建议胜过五条空泛的；真的没东西就明说，不要硬凑。

## 步骤 3：查重（过滤后留下的每条候选都要做，不可跳过）

索引只列到「页」——已有知识常是某页里的一个小节，光看档名或索引看不到。所以：

1. 从 session 开场注入的主题索引摘要出发（不在 session 里就读知识库根的 `index.md`），
   对话触及的主题 → 读对应 `index-<slug>.md` 看该主题已有哪些页。
2. **每条候选知识都跑一次搜索**，把同义词/别名一起丢进去（多个关键字任一命中即列出）：
   `node "${CLAUDE_PLUGIN_ROOT}/scripts/wiki-search.js" <关键字1> <关键字2> ...`
3. **读命中的小节**（输出带小节标题与行号），判断既有内容涵盖到哪：
   - 完全涵盖 → 不提案。
   - 部分涵盖 → 提案改成「更新 X.md〈小节〉」，只提增量。
   - 没命中 → 才提新页／新小节。
4. 把查重结果写进提案的「查重」行（见步骤 4）。没跑搜索就不要写「无命中」。

## 步骤 4：输出盘点

```text
Wiki 盘点

本轮涉及：[一句话]

建议更新：

1. <页名>.md（新增/更新）— [要记什么]
   - 白话: [一句人话——这是什么、为何值得记、不记会怎样。除非 proposalStyle=terse，必给]
   - type: Pitfall/Guide/Reference/Decision
   - 来源: [对话哪一步、哪个档案、哪次实测]
   - 查重: [搜了哪些关键字 → 命中哪页哪节（或无命中）→ 结论：新页／扩写 X.md〈小节〉]
   - 预期内容: [2-3 句]

（或）无需 wiki 更新：[为什么没有]

要套用这些建议吗？
```

**查重行必填**——用户靠它一眼确认「这条真的查过、不是重复的」。

**白话行是给「不一定是该领域专家、也可能在手机上」的用户判断用的**——别只丢术语/
代码/档名，用户还得翻上下文才懂就失败了。一句话说清「记这个是为了让谁以后少踩什么」。

## 步骤 5：写入遵循政策

- `require_approval`（预设）：等用户明确同意才动手。
- 写入时必须：补齐 frontmatter（`type` 必填）→ 更新对应 `index-<slug>.md` → 更新 `index.md` 页数。四种维护情境的 checklist 见 reference.md。
- 进度/待办不进知识库（写专案的 state 目录）；memory 已停用，不写。
